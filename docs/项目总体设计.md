# AetherServe · 项目总体设计

> 项目代号：**AetherServe**
> 定位：面向大模型的多租户云原生推理服务平台
> 开发环境：Windows 11 + i7-13700H (14C/20T) + RTX 4060 Laptop 8GB + 16GB RAM
> 集群环境：kind（本地 Kubernetes）

---

## 一、项目定位

> **AetherServe：面向大模型的多租户推理服务平台。以 OpenAI 兼容协议对外提供服务，
> 通过自研批处理调度引擎提升 GPU 吞吐，通过 Kubernetes Operator 实现推理服务的声明式管理与弹性伸缩。**

**它要解决的问题**：大模型推理的成本瓶颈在 GPU。多数团队直接用"一次请求一次前向"的方式调模型，
结果是 GPU 利用率长期在个位数百分比徘徊；而一旦并发上来，延迟又会线性恶化——
本质是**吞吐与延迟没有被解耦**。

**它提供的三件事**：
1. **协议层**：OpenAI 兼容对外接口（业务方零改造迁移）+ 多租户鉴权限流；
2. **调度层**：把离散请求聚合成批送给 GPU，用批处理摊薄显存带宽成本；
3. **控制面**：把"我要一个模型服务"变成声明式 CRD，由 Operator 持续收敛。

### 数据流（一次流式推理请求）

```
Client ──POST /v1/chat/completions(stream=true)──▶ Gateway
   Gateway: 鉴权 → 限流 → 熔断准入 → 构造请求 ──▶ BatchingEngine.submit()
   BatchingEngine: 入优先级队列 → 分发循环按 (显存水位, 批大小上限, 等待时延) 组装批
        ──▶ Backend.generate() ──▶ vLLM（PagedAttention 连续批）
        ◀── token 流（批内按 request_id 多路分解到各自私有队列）
   Gateway ◀── 逐 token 封装为 SSE data: {...}\n\n ──▶ Client
   Metrics: 各阶段打点（queue_wait_ms, batch_size, ttft_ms, tpot_ms）
```

## 四、技术栈清单

| 层次 | 技术 | 选型理由 |
|---|---|---|
| 语言 | **Python 3.11 / 3.12** | 原生 async 支持完善；AI 生态（vLLM/Transformers）以 Python 为主 |
| Web 框架 | **FastAPI + uvicorn** | 原生 async、pydantic 校验、自动生成 OpenAPI 文档 |
| 推理引擎 | **vLLM**（PagedAttention / 连续批 / AWQ 量化） | 当前主流 LLM 推理引擎，显存利用率显著优于朴素实现 |
| 兼容后端 | **HuggingFace Transformers** | 覆盖小模型与纯 CPU 场景 |
| 容器编排 | **Kubernetes 1.29+**（本地 kind） | 声明式 API + 控制器模式，是云原生交付的事实标准 |
| Operator 框架 | **kopf**（Python） | 与主语言一致，降低维护成本；支持 resume/timer 等完整事件模型 |
| 监控 | **Prometheus + Grafana** | 云原生观测事实标准；自定义指标可通过 adapter 驱动 HPA |
| HTTP 客户端 | **httpx**（连接池） | 异步 + 连接复用，避免每请求三次握手 |
| 数据校验 | **pydantic v2** | 协议模型与 CRD 模型的统一校验层 |
| 压测 | 自研负载驱动 + **locust**（HTTP 端到端） | 自研版本可隔离调度层性能，不受网络噪声干扰 |
| 质量 | **pytest / ruff / mypy** | 单测 + 静态检查 + 类型检查，CI 全量执行 |
| CI/CD | **GitHub Actions** | 5 个 job：lint / test(双版本) / benchmark / manifests / build |
| 交付 | **Docker 多阶段构建 + Helm** | 镜像瘦小、非 root 运行；Helm 管理控制面生命周期 |

## 六、关键设计取舍（详见 [架构设计.md](架构设计.md)）

| 设计点 | 取舍 |
|---|---|
| 三层拆分（网关/引擎/执行器） | 变化频率与扩缩容维度不同；代价是一次进程间跳转（约 0.1ms） |
| 准入控制快速失败 | 保整体可用性；代价是被拒请求需上游重试 |
| 惰性堆实现动态优先级 | 避免索引堆复杂度；代价是弹出时需重排队首 |
| 每请求私有 chunk 队列 | 天然多路复用与背压；代价是每请求一个队列对象 |
| 聚合类不继承 BaseSettings | 消除父子环境变量名冲突（曾导致生产启动崩溃）；代价是需显式 `from_env()` |
| 调和逻辑做成纯函数 | 可完整单测；代价是与集群 I/O 分离需额外分层 |
| 性能数据用仿真 + 独立自校验 | 无 GPU 也能量化收益；代价是需额外维护校验工具链 |

## 七、风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| 16GB 内存同时跑集群与推理吃紧 | OOM | kind 限 1 控制面 + 2 工作节点；推理用 1.5B AWQ 量化模型；必要时推理跑宿主机、K8s 只做编排 |
| kind 内 GPU 透传复杂 | 拿不到真实 GPU 指标 | 集群侧重 CPU 侧验证；GPU 指标由宿主机提供；调度策略以仿真验证为主 |
| 批在派发后不变（等满发车） | 批内长短请求差异大时尾延迟劣化 | 真正的连续批调度交由下游 vLLM；演进方向是批执行器支持请求中途进出 |
| 集群 I/O 层无法单测 | 潜在集成缺陷 | 提供完整部署指南（[部署与本地验证.md](部署与本地验证.md)），在 kind 上做端到端验证 |
