# 架构设计说明

> 本文档回答"**为什么这么设计**"，而不是"有哪些模块"。
> 模块清单与实施路线见 [`项目总体设计.md`](项目总体设计.md)。

---

## 1. 全局架构决策

### 1.1 为什么把系统分成"网关 / 引擎 / 执行器"三层？

**决策**：网关（协议与租户）→ 引擎（准入与批调度）→ 执行器（vLLM 等）。

**动因**：这三层的**变化频率和扩缩容维度完全不同**。

| 层 | 变化频率 | 扩缩容维度 | 故障域 |
|---|---|---|---|
| 网关 | 中（协议、鉴权策略） | 按 QPS 横向扩 | 可重启，无状态 |
| 引擎 | 高（调度策略、压测调参） | 与网关同进程 | 单请求隔离 |
| 执行器 | 低（模型、量化方式） | **按 GPU 显存扩** | 崩了不该拖垮控制面 |

**收益**：
- 调度策略可以独立演进和压测，**不需要重新编译推理引擎**；
- 网关镜像保持瘦小（不含 CUDA/torch），HPA 冷启动更快；
- 一个 vLLM 实例崩溃不会让协议层一起挂掉。

**代价**：网关与执行器之间多一次进程间网络跳转（本机回环约 0.1ms，
跨节点约 0.3ms）。相对推理本身几十毫秒的开销可以忽略，换来清晰的故障域。

### 1.2 依赖方向必须单向（这条被违反过一次）

```
backends ──▶ gateway.schemas          （只依赖协议模型）
gateway.app ──▶ engine ──▶ backends    （装配方向）
operator: crd ─▶ builders/canary ─▶ reconciler ─▶ handlers
```

**踩过的坑**：`backends.base` 需要 `ChatMessage` 模型，
而 `gateway/__init__.py` 在导入时就去加载 `app`（`app` 又反向依赖 `backends`），
形成**循环导入**。

**修法**：`gateway/__init__.py` 改用 PEP 562 的模块级 `__getattr__` 惰性导出，
让 `gateway.schemas` 能被安全地单独引用。

**约束**：新增模块前必须确认依赖方向，**不允许反向依赖**。

## 2. 调度层设计

### 2.1 为什么准入控制要"快速失败"而不是"无限排队"？

**决策**：队列长度 + 在途 token 双阈值，超出直接返回 429。

**动因**：GPU 吞吐是固定的。请求无限堆积的后果**不是"变慢"，而是系统崩溃**：

```
请求堆积 → 每个在途请求都要预留 KV Cache → 显存压力上升
        → 达到上限时触发 OOM 或疯狂 swap → 延迟无界增长 → 所有请求一起失败
```

**收益**：过载时保住系统整体可用性——让一部分请求快速失败（上游可以重试/降级），
而不是让全部请求一起烂掉。这与 Hystrix 的 bulkhead、K8s 的 overload 保护同源。

**代价**：被拒绝的请求需要上游配合重试，因此我在 429 响应里带了
`Retry-After` 和明确的错误码，让上游能做正确的退避。

### 2.2 为什么用"惰性堆"实现动态优先级？

**问题**：优先级随等待时长动态变化（老化），而标准堆不支持修改元素优先级。
维护"可更新优先级的堆"需要索引堆（元素 → 堆位置的反向索引），
实现复杂且容易出错。

**决策**：惰性堆。弹出时用**当前时刻**重算有效优先级；
若因老化变得更优先，则 `heapreplace` 重新入堆并重试。

**为什么这是对的**：
- 每次只可能重塑**队首**（老化对等待最久的元素奖励最大），
  所以重排循环实际迭代次数极少（我设了 4 次的有界上限）；
- 复杂度仍是 O(log n)，无需额外索引结构；
- 代码量小、易测试。

**不变式**（我在测试里断言）：重排后 `heap[0]` 是全堆有效优先级最小的元素。

### 2.3 批构建的三个旋钮为什么是这三个？

| 旋钮 | 约束什么 | 调大的后果 | 调小的后果 |
|---|---|---|---|
| `max_batch_size` | attention 计算量与并发度 | 单步变慢、显存压力大 | 吞吐上不去 |
| `max_batch_tokens` | KV Cache 占用峰值 | 有 OOM 风险 | 批装不下长请求 |
| `max_wait_ms` | **延迟与吞吐的权衡点** | 批更大、吞吐高、TTFT 差 | 延迟低、吞吐下降 |

**为什么 token 维度和请求数维度都要有**：因为成本主要由 token 数决定，
10 个长请求和 10 个短请求的显存占用差两个数量级。
只按请求数限批会在长 prompt 场景下爆显存。

### 2.4 显存预算的记账原则：**在哪扣就在哪还**

**决策**：显存记账（`_inflight_tokens`）只在两个地方操作：
- `put()` 时**加上**；
- `_drain()` 把请求摘除时**减去**（无论执行成功、失败还是被取消）。

**为什么这个原则重要**：我最初的实现里，`cancel()` 只标记了取消位，
没有触发记账归还，导致队列会"**假满**"——已取消的请求还占着预算，
新请求被无谓地拒绝。同类问题还有"请求在等待中被取消"的路径。

**测试保障**：任何请求结束后，`inflight_tokens` 必须归零。
这是我在多个测试里断言的不变量。

## 3. 网关层设计

### 3.1 为什么每个请求一个私有 chunk 队列？

**替代方案对比**：

| 方案 | 问题 |
|---|---|
| 单一共享队列 | 慢客户端会拖累批内其他请求；消费侧要自己做 request_id 分流 |
| 回调函数 | 异步上下文里容易出错；取消传播复杂 |
| **每请求私有队列（选用）** | 天然多路复用、天然背压、取消简单（投 sentinel） |

**实现**：`RequestHandle` 持有一个 `asyncio.Queue`，
批执行器按 request_id 把 token 分发到对应队列，调用方 `async for` 消费自己的队列。

### 3.2 为什么熔断器要按后端实例维度而非全局？

**决策**：`CircuitBreakerRegistry` 按后端名管理多个独立熔断器。

**动因**：不同后端（vllm / transformers / echo）的可用性相互独立。
如果全局一个熔断器，A 后端挂了会导致 B 后端也被熔断——**故障被错误放大**。

**状态机细节**：半开态探测失败必须**立即重新打开**，不做二次观察。
灰度和熔断的共同原则是"限制爆炸半径，犹豫等于放大损失"。

### 3.3 为什么用一致性哈希而不是轮询做路由？

**动因**：**KV Cache 亲和性**。
vLLM 的 Automatic Prefix Caching 会缓存已计算的 prompt 前缀，
同一会话（相同 messages 前缀）落到同一实例就能命中缓存，
对长 system prompt 场景能显著降低 TTFT。

**为什么可以安全使用**：
- 实例集合变化导致哈希环变化时，普通请求只是**失去缓存收益，不会失败**；
- 只有正在处理中的流式请求会受影响，实践上配合"优雅摘除"（先停新流量再下线）即可。

**代价**：负载可能不均（哈希倾斜）。我用虚拟节点（权重 × 64）缓解，
并在只有单实例时退化为轮询。

## 4. 控制面（Operator）设计

### 4.1 为什么把调和逻辑做成不依赖集群的纯函数？

**决策**：`plan_reconcile(cr, existing, metrics) -> ReconcilePlan` 不读也不写集群。

**动因**：如果把决策逻辑写在 kopf 处理器里，验证方式只剩
"改集群 + 等 5 分钟看结果"，成本高到没人会测。

**收益**：
- 全部边界（资源缺失、spec 变更、灰度推进、孤儿清理、校验失败）
  都能在毫秒级单测里覆盖；
- 换掉 kopf（改用 Go controller-runtime）时决策逻辑可原样复用。

**分层**：`reconciler` 算"做什么"，`handlers` 只负责"读集群 → 调计划 → 写集群"。
后者几乎没有业务分支，出错面很小。

### 4.2 标签设计：为什么版本必须用独立标签？

这个设计缺陷我踩过，值得单独说。

**问题**：我最初把版本塞进 `app.kubernetes.io/instance`（如 `demo-stable`），
同时踩了两个坑：

1. **Service 选不到 Pod**：Service 的 selector 写成 `instance=demo-stable`，
   而 Pod 模板的标签是 `instance=demo` → 服务起得来但**访问不通**。
2. **灰度流量失控**：稳定版 selector 只匹配 `instance` 时，
   会把灰度 Pod 也选中 → 稳定版和灰度版的流量彻底串了。

**正确设计**：版本用**专属标签** `aetherserve.io/role`（`stable` / `canary`）表达，
`instance` 只承载业务实例名。

```
app.kubernetes.io/name       = aetherserve       产品名
app.kubernetes.io/instance   = <CR 名称>          业务实例（不含版本）
app.kubernetes.io/component  = gateway            组件
aetherserve.io/role          = stable | canary    ★ 唯一的版本判别维度
aetherserve.io/cr            = <CR 名称>          供 ServiceMonitor 交集匹配
app.kubernetes.io/managed-by = aetherserve-operator  孤儿清理的安全依据
```

**结构性保障**：Deployment 的 selector 与 Service 的 selector
**由同一个函数产出**（`selector_labels(name, role)`），
从结构上消除"两者写得不一致"的可能性。

命名规范遵循 K8s 惯例（`app.kubernetes.io/*`），因为 Prometheus Operator、
Grafana、kubectl 插件等生态工具都按这套约定发现资源。

### 4.3 不可变字段的处理

**约束**：K8s 规定 Deployment 的 `spec.selector` **创建后不可修改**。

**推论**：selector 只能由**不可变量**组成。我用「CR 名 + 固定角色字面量」，
**绝不包含 spec hash**（hash 会随配置变化）。

**那怎么触发滚动更新**：把 spec hash 写进 **Pod 模板的 annotation**。
annotation 是可变的，改它会触发 Pod 重建；
而 selector 不变，Deployment 就能正常更新。

```yaml
spec:
  selector:                    # 永不变（只含name+role）
    matchLabels: {app.../instance: demo, aetherserve.io/role: stable}
  template:
    metadata:
      annotations:
        aetherserve.io/spec-hash: "a1b2c3d4"   # ★ 变化时才滚动
```

### 4.4 为什么用 ownerReference 而不是手写级联删除？

**动因**：手写删除逻辑容易漏删——比如以后新增一种资源类型忘了加清理代码，
最后留下"没人管但仍在消耗 GPU"的 Pod。

**ownerReference 的收益**：K8s 自己处理级联回收，新增资源类型自动获得该能力。

**但孤儿清理仍需手写**（灰度回滚后 canary 资源不再属于期望状态）——
这时必须有**安全检查**：只删带 `managed-by` 标签的资源，避免误删他人资源。
归属判断优先用 ownerReference 的 **uid**，而不是按资源名做子串匹配
（后者在多个 CR 名字互为前缀时会张冠李戴）。

### 4.5 为什么监控不可用时灰度要"停住"？

**决策**：`_fetch_canary_metrics` 失败时返回空指标，
而空指标会走"样本不足"分支 → 权重保持不变。

**原则**：**fail-safe 而不是 fail-open**。
监控挂了说明我们对灰度状态"看不见"，此时最安全的动作是什么都不做。
如果设计成 fail-open（拿不到指标就当健康），监控一挂就会全量发布，风险极大。

**同类设计**：灰度推进必须满足最小样本量门禁。否则一个只收到 3 个请求、
恰好全成功的灰度版会被误判为"健康"直接全量——这是灰度发布最经典的事故模式。

## 5. 可观测性设计

### 5.1 为什么要有 LLM 专项指标？

传统 Web 服务的 RED 指标（Rate / Error / Duration）**无法定位推理性能瓶颈**，
因为一次推理请求的延迟由三段构成：

```
排队 → Prefill（算力受限）→ Decode 逐 token（显存带宽受限）
```

所以我定义了 LLM 专项指标：

| 指标 | 含义 | 定位什么 |
|---|---|---|
| `ttft_seconds` | 首 token 时间 | **用户感知延迟**的核心 |
| `tpot_seconds` | 相邻 token 间隔 | 解码速度 |
| `batch_size` | 每次批执行的请求数 | **批处理是否真的生效** |
| `batch_tokens` | 批的 token 预算占用 | 显存压力 |
| `queue_depth` / `queue_wait_seconds` | 队列状态 | 背压与扩容信号 |
| `inflight_tokens` | 在途 KV 预估值 | 显存预算使用量 |
| `preemptions_total{reason}` | 背压拒绝数 | 容量规划依据 |
| `circuit_breaker_state` | 熔断状态 | 后端健康度 |

**`batch_size` 是我最看重的指标**：如果它长期是 1，说明批处理没生效——
这正是我在开发中发现问题的那条路径。

### 5.2 日志为什么要注入 request_id？

**动因**：分布式系统中"问题定界定位"的第一步是**请求可追踪**。

**实现**：用 `contextvars` 把 `request_id` / `tenant` 注入日志上下文，
业务代码无需层层传参，全链路日志自动带上同一个 request_id。
输出为 JSON，便于 ELK / Loki 采集与检索。

## 6. 性能数据的可信度设计

这是本项目**最值得讲**的一段工程实践。

### 6.1 问题：仿真数据凭什么可信？

性能结论是本项目的核心交付之一，但真实 GPU 环境不可用。
用仿真数据有两个风险：① 模型不对；② 实现有 bug 导致"看起来合理"。

### 6.2 解法：三层交叉验证

| 层 | 做什么 | 输出 |
|---|---|---|
| ① 解析模型 | 纯公式计算理论耗时 | 期望值 |
| ② 实测睡眠 | 仿真后端累加真实 `await` 时长（**每步只记一次**） | 接近 ① 的值 |
| ③ 端到端墙钟 | 实测 | 接近 ② 的值 |

**判定**：`① < ② < ③`，且 **② vs ③ 偏差 < 15%** 才算通过。
`①→②` 的差额是 asyncio 定时器精度（Windows 粒度约 15ms），
`②→③` 的差额是调度框架开销。用 ① 直接校验 ③ 是不公平的。

### 6.3 这个方法真的抓到了 bug

第一版仿真跑出"批处理比串行快 **108 倍**"——明显荒谬。
自校验显示偏差 **91%**，据此定位到两个实现缺陷：

1. **按"每请求独立计时"而非"整批共享一次解码步"**。
   真实引擎的解码是把活跃请求融合成一次前向，不是各跑一次。
   修法是引入**批同步屏障**（batch rendezvous）：同批请求在同一解码步上同步，
   只等待一次 `decode_step_ms(B)`。
2. **统计重复计数**：16 个请求会把同一次共享睡眠各记一次，统计虚高 16 倍。
   修法是只在屏障内部累加一次真实耗时。

修正后：**模型加速比 9.00× / 实测 9.45× / 解析单步增益 10.24×**，三者互相印证。

### 6.4 文档数字的自动对账

为避免"报告里写 4.9× 而原始数据算出来是 3.2×"这类不一致，
我写了 `bench/verify_claims.py`，把文档中引用的每个关键数字
与 `bench/results/` 下的原始数据自动比对，容差内才算通过。

**这个习惯的价值**：任何人对数据有疑问时，
都能用一条命令复现出同样的结果，而不是只能相信文档里的文字。

## 7. 已知设计局限（主动声明）

| 局限 | 影响 | 演进方向 |
|---|---|---|
| **批在派发后不变**（等满发车，非 iteration-level 连续批） | 批内长短请求差异大时尾延迟劣于真正的连续批 | 批执行器改为"活跃请求集合 + 每步重算" |
| **GPU 调度器插件未实现** | 多模型混部时显存装箱靠 K8s 默认调度 | 用 Go 写 Scheduler Framework 的 Filter/Score |
| **`handlers.py` 未覆盖单测** | 集群 I/O 层需真实集群验证 | WSL2 + kind 端到端测试 |
| **未做多副本负载均衡实测** | prefix cache 复用收益未经数据验证 | kind 上起 3 副本 + locust 端到端压测 |
| **仿真未模拟 OOM/preemption** | 真实显存耗尽时的尾延迟尖峰未覆盖 | 在仿真里加入 swap 惩罚模型 |

## 8. 踩坑记录：一个"本地永远测不出、生产必然踩"的配置 bug

这个 bug 值得单独记录，因为它的**暴露路径**比 bug 本身更有教学价值。

### 8.1 现象

CI 的镜像 smoke test 失败：容器启动后立刻退出。

### 8.2 根因

配置系统设计缺陷 —— **父子配置类争夺同一个环境变量名**：

```python
class Settings(BaseSettings):                    # env_prefix = "AETHERSERVE_"
    backend: BackendSettings = ...               # ← 字段名 backend

class BackendSettings(BaseSettings):             # env_prefix = "AETHERSERVE_"
    backend: str = "echo"                        # ← 字段名也叫 backend
```

于是 `AETHERSERVE_BACKEND=echo` 产生歧义：
pydantic-settings 认为它在给父类的**复杂类型字段** `backend` 赋值，
于是尝试把字符串 `echo` 当 JSON 解析 → `JSONDecodeError` → **进程启动即崩溃**。

### 8.3 为什么本地和单测都发现不了

| 场景 | 是否设环境变量 | 结果 |
|---|---|---|
| 本地开发 | ❌ 用代码默认值 | 正常 |
| 单元测试 | ❌ 直接 `Settings()` | 正常 |
| **容器/K8s 部署** | ✅ **通过环境变量注入配置** | **崩溃** |

这就是它危险的地方：**开发路径与生产路径的配置加载方式不同**，
而我只测了开发路径。

### 8.4 修法

1. 聚合类 `Settings` 改用 `BaseModel`（**不参与环境变量解析**），
   子配置块在 `from_env()` 里显式构造 → 从结构上消除父子字段名冲突；
2. 补 `tests/test_config.py` 做回归保护：
   用**子进程**逐一注入每个环境变量（必须新进程，因为 env 要在解释器启动前生效），
   并断言 `Settings` 不继承 `BaseSettings`；
3. 加固 CI smoke test：用**与生产一致的方式**注入环境变量，
   并在容器提前退出时立即打印日志（而不是空等 30 秒）。

### 8.5 可迁移的教训

> **测试要贴近真实部署路径。**
> 只测"进程内构造对象"会漏掉"从环境变量/配置文件/命令行加载"这一整类问题。
> 一个 `docker run -e ...` 的 smoke test 就能覆盖这类风险，成本极低。

同类需要警惕的场景：从 ConfigMap 挂载的配置文件、命令行参数解析、
多环境配置合并（dev/staging/prod 覆盖顺序）——它们的共同点是
**本地默认路径与线上注入路径不同**。
