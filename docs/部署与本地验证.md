# 部署与本地验证指南

> 本文档给出**从零到跑通**的完整步骤：本地开发 → kind 集群 → Helm 部署 → Operator 验证。
> 实测环境：Windows 11 + RTX 4060 Laptop 8GB + 16GB RAM。

---

## 0. 环境要求与依赖清单

| 组件 | 版本要求 | 用途 | 是否必需 |
|---|---|---|---|
| Python | 3.11 / 3.12 | 网关与 Operator | ✅ 必需 |
| WSL2 + Ubuntu | 22.04 / 24.04 | 容器与集群的 Linux 环境 | ✅ 集群验证必需 |
| Docker Desktop | 最新版（勾选 WSL 2 后端） | 构建镜像、运行 kind | ✅ 集群验证必需 |
| kind | ≥ 0.20 | 本地 Kubernetes 集群 | ✅ 集群验证必需 |
| kubectl | ≥ 1.29 | 集群操作 | ✅ 集群验证必需 |
| Helm | ≥ 3.14 | 部署 Chart | 推荐 |
| NVIDIA 驱动 + CUDA | 驱动 ≥ 535 | vLLM 真实推理 | 可选（有 GPU 才需要） |

> **没有 GPU 也能完成全流程**：`echo` 后端是确定性假后端，
> 可以完整验证协议、调度、Operator 与监控链路。真实推理是可选的加餐。

## 1. 第一步：Windows 侧安装 WSL2

以**管理员身份**打开 PowerShell：

```powershell
# 安装 WSL2 与 Ubuntu（会要求重启一次）
wsl --install -d Ubuntu-24.04

# 重启后 Ubuntu 会让你设置用户名与密码
```

重启后进入 Ubuntu，装基础工具：

```bash
sudo apt update && sudo apt install -y python3-venv python3-pip make curl git jq
```

**验证**：

```bash
wsl -l -v          # 应显示 Ubuntu-24.04 且 VERSION 为 2
```

---

## 2. 第二步：安装 Docker / kubectl / kind / helm

```powershell
# 1) 安装 Docker Desktop（安装时务必勾选 "Use WSL 2 based engine"）
#    https://www.docker.com/products/docker-desktop/

# 2) 用 winget 安装其余工具
winget install Kubernetes.kubectl
winget install Helm.Helm
winget install Kubernetes.kind
```

**验证**（新开一个 PowerShell）：

```powershell
docker version          # 应显示 Client 与 Server
kubectl version --client
kind version
helm version
```

**Docker Desktop 设置建议**（本项目在 16GB 内存机器上验证过）：
- Resources → Memory：至少 **6GB**
- Resources → CPUs：至少 **4**
- 如果内存紧张，把 kind 节点数从 3 降到 2（见第 4 步）

---

## 3. 第三步：本地开发（不需要集群，5 分钟跑通）

```powershell
cd D:\deepseek-harness\default-workspace\myinter

# 创建虚拟环境并安装依赖
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -U pip
.\.venv\Scripts\python.exe -m pip install -e ".[dev,operator]"

# 跑测试确认基线（应为 302 passed）
.\.venv\Scripts\python.exe -m pytest tests/ -q
```

启动网关：

```powershell
.\.venv\Scripts\python.exe -m uvicorn aetherserve.gateway.app:app --port 8000
```

另开一个窗口验证：

```powershell
# 1) 健康检查
curl.exe http://localhost:8000/healthz

# 2) 列出模型
curl.exe http://localhost:8000/v1/models -H "Authorization: Bearer sk-demo-001"

# 3) 流式对话（-N 关闭 curl 缓冲，否则看不到逐字效果）
curl.exe -N http://localhost:8000/v1/chat/completions `
  -H "Authorization: Bearer sk-demo-001" `
  -H "Content-Type: application/json" `
  -d "{\"model\":\"echo-1\",\"messages\":[{\"role\":\"user\",\"content\":\"你好\"}],\"max_tokens\":8,\"stream\":true}"

# 4) 查看指标
curl.exe http://localhost:8000/metrics | Select-String "aetherserve_batch_size"
```

预期：第 3 步看到逐条 `data: {...}` 事件，最后是 `data: [DONE]`。

---

## 4. 第四步：创建 kind 集群

```powershell
# 用仓库提供的集群定义（1 控制面 + 2 工作节点，节点带模拟 GPU 标签）
kind create cluster --name aetherserve --config deploy\local\kind-cluster.yaml

# 验证
kubectl get nodes --show-labels | Select-String "accelerator"   # 应看到 nvidia 标签
```

**为什么节点要打 `aetherserve.io/accelerator=nvidia` 标签**：
这样不带真实 GPU 也能验证 `nodeSelector` / `tolerations` 这条调度路径
（即"GPU 服务是否真的只被调度到 GPU 节点上"）。

**内存不足时的降级方案**：编辑 `deploy/local/kind-cluster.yaml`，
删掉第二个 worker 节点，然后重建集群。

---

## 5. 第五步：构建镜像并加载进集群

kind 集群不能直接拉本地镜像，需要 `kind load`：

```powershell
# 构建网关镜像
docker build -t aetherserve/gateway:0.1.0 .

# 加载进 kind 集群（kind 要求镜像已存在于本地）
kind load docker-image aetherserve/gateway:0.1.0 --name aetherserve

# 验证镜像已在节点上
docker exec aetherserve-worker crictl images | Select-String gateway
```

**镜像设计说明**：
- **多阶段构建**：builder 阶段装 `build-essential` 编译依赖，runtime 阶段只保留运行时，
  避免把编译器带进生产镜像；
- **非 root**（uid 10001）：与 Operator 生成的 Pod securityContext 一致；
- **tini 作为 PID 1**：保证 SIGTERM 能传到 uvicorn，触发引擎的优雅停机；
- **不含 CUDA/torch**：网关不需要 GPU，保持镜像瘦小以加快 HPA 冷启动。

## 6. 第六步：部署平台（CRD + Operator + 监控）

```powershell
# 1) 安装 CRD（从代码生成，保证"代码即契约"）
.\.venv\Scripts\python.exe deploy\k8s\generate_manifests.py --all --out deploy\k8s\aetherserve-crd.yaml
kubectl apply -f deploy\k8s\aetherserve-crd.yaml

# 2) 验证 CRD 与 kubectl 打印列
kubectl get crd inferenceservices.aetherserve.io
kubectl explain inferenceservice.spec.canary

# 3) 创建命名空间
kubectl create namespace ai-serving

# 4) 创建示例 InferenceService（先用 echo 后端，不需要 GPU）
kubectl apply -f - <<'EOF'
apiVersion: aetherserve.io/v1alpha1
kind: InferenceService
metadata:
  name: echo-demo
  namespace: ai-serving
spec:
  model: echo-1
  backend: echo
  replicas: 1
  autoscaling:
    enabled: true
    minReplicas: 1
    maxReplicas: 3
    metrics: ["queue_depth"]
EOF
```

> **注意**：`backend: echo` 时不能申请 GPU（`resources.gpu > 0`），
> 校验会拒绝——这是刻意的安全约束，避免假后端白占显卡。

## 7. 第七步：本地运行 Operator（集群外）

Operator 支持集群外运行（读 `~/.kube/config`），便于开发调试：

```powershell
# 设置 Prometheus 地址（可选，用于灰度分析；不设置则灰度会停在原地）
$env:AETHERSERVE_PROMETHEUS_URL = "http://localhost:9090"

.\.venv\Scripts\python.exe -m aetherserve.operator.main --verbose
```

**验证 Operator 是否工作**（另一个窗口）：

```powershell
# 1) 查看 Operator 生成的全部资源
kubectl get deployment,service,hpa,poddisruptionbudget -n ai-serving

# 预期看到 4 类资源：
#   deployment/echo-demo-gateway
#   service/echo-demo-stable
#   horizontalpodautoscaler/echo-demo-hpa
#   （replicas=1 时不会创建 PDB）

# 2) 查看 CR 状态是否被回写
kubectl get isvc -n ai-serving -o yaml | Select-String -Pattern "status" -Context 0,20

# 3) 用 kubectl 的自定义列查看（CRD 里定义的 printer columns）
kubectl get isvc -n ai-serving
# 预期输出含 Model / Backend / Replicas / Ready / Canary / Age 列
```

**验证幂等性**（这是 Operator 最关键的性质）：

```powershell
# 记录当前 Deployment 的 Pod 数量与重启次数
kubectl get pods -n ai-serving

# 手动触发一次调和（改一个无关字段再改回来，或直接等 Operator 的 watch）
# 观察：Pod 不应被重建（RESTARTS 保持 0，AGE 持续增长）
kubectl get pods -n ai-serving -w
```

**验证 spec 变更触发滚动更新**：

```powershell
kubectl patch isvc echo-demo -n ai-serving --type=merge -p '{"spec":{"maxBatchSize":32}}'
kubectl get pods -n ai-serving -w   # 应看到 Pod 被重建（AGE 归零）
kubectl get deployment echo-demo-gateway -n ai-serving -o jsonpath='{.spec.template.metadata.annotations}'
# 应看到 aetherserve.io/spec-hash 已变化
```

**验证级联回收**：

```powershell
kubectl delete isvc echo-demo -n ai-serving
kubectl get deployment,service,hpa -n ai-serving
# 预期：所有子资源都被自动清理（靠 ownerReference）
```

## 8. 第八步：接入监控（可选但推荐）

```powershell
# 用 kube-prometheus-stack 起 Prometheus + Grafana
helm repo add prometheus-community https://prometheus-community.github.io/helm-charts
helm repo update
helm install monitoring prometheus-community/kube-prometheus-stack `
  --namespace monitoring --create-namespace `
  --set prometheus.prometheusSpec.serviceMonitorSelectorNilUsesHelmValues=false `
  --set grafana.adminPassword=admin
```

**关键配置**：`serviceMonitorSelectorNilUsesHelmValues=false`
——否则 Prometheus 只认 Helm 自己的 ServiceMonitor，我们生成的抓不到。

```powershell
# 端口转发访问
kubectl port-forward -n monitoring svc/monitoring-grafana 3000:80
# 浏览器打开 http://localhost:3000，账号 admin / admin
```

**建议在 Grafana 里建的面板**（对应我们暴露的指标）：
1. **吞吐与延迟**：`rate(aetherserve_requests_total[1m])` + TTFT P99 的 histogram_quantile；
2. **批处理健康度**：`histogram_quantile(0.5, rate(aetherserve_batch_size_bucket[5m]))`
   —— **这条最该看**，如果长期接近 1 说明批处理没生效；
3. **队列与背压**：`aetherserve_queue_depth` + `aetherserve_inflight_tokens`；
4. **熔断状态**：`aetherserve_circuit_breaker_state`（0/1/2）。

## 9. 第九步：真实 GPU 推理（可选）

前提：WSL2 里有 NVIDIA 驱动（Windows 驱动自带 WSL 支持，`nvidia-smi` 能在 WSL 里跑通）。

```bash
# 在 WSL2 Ubuntu 里
pip install vllm

# 起 vLLM 的 OpenAI 兼容服务，Qwen2.5-1.5B AWQ 量化版约 1GB 权重，8GB 显存够用
python -m vllm.entrypoints.openai.api_server \
  --model Qwen/Qwen2.5-1.5B-Instruct-AWQ \
  --quantization awq \
  --max-model-len 4096 \
  --gpu-memory-utilization 0.85 \
  --port 8001
```

然后让网关指向它：

```bash
export AETHERSERVE_BACKEND=vllm
export AETHERSERVE_VLLM_ENDPOINT=http://127.0.0.1:8001
export AETHERSERVE_MODEL=Qwen/Qwen2.5-1.5B-Instruct-AWQ
uvicorn aetherserve.gateway.app:app --port 8000
```

跑真实压测并**替换性能报告中的数据**：

```bash
python bench/run_bench.py --mode vllm --endpoint http://127.0.0.1:8001 \
  --concurrency 1,8,16,32 --requests 64 --max-tokens 32 --prompt-tokens 256
```

> ⚠️ **采集到真实数据后**，请同步更新两处，保持数字一致：
> ① `docs/性能测试报告.md`（含"关于耗时模型的声明"）；
> ② `README.md` 的性能数据表。
> 并用 `python bench/verify_claims.py` 对账。

## 10. 常见问题排查

| 现象 | 原因 | 处理 |
|---|---|---|
| `WinError 10055` 系统缓冲区不足 | 反复压测导致内核套接字内存池耗尽 | 等待 20-30 秒后重试；减少压测轮次 |
| Operator 不生成任何资源 | CRD 未装 / `resume` 未触发 / 校验失败 | `kubectl describe isvc <name>` 看 status 与事件；确认日志有 `reconciled` |
| Service 起得来但访问不通 | selector 与 Pod 标签不一致 | `kubectl get endpoints <svc>` 若为空说明选不到 Pod |
| 灰度一直停在初始权重 | Prometheus 未接 / 样本不足 | 查 `AETHERSERVE_PROMETHEUS_URL`；确认指标有数据 |
| HPA 不扩容 | 自定义指标未接入 | 需要 prometheus-adapter 暴露 `custom.metrics.k8s.io` |
| kind 节点 OOM | 内存配额太小 | Docker Desktop 提高内存，或减少 worker 节点 |
| Pod 一直 Pending | 申请了 GPU 但节点无 GPU 资源 | 示例里 `backend: echo` 不要申请 GPU；真实 GPU 需装 device plugin |

**排查顺序建议**（这是我实际用的路径）：
`kubectl describe pod` → `kubectl logs` → CR 的 `status` → Operator 日志 → Prometheus 指标。

## 11. 一键命令速查

> **Windows 用户注意**：`make` 在 Windows PowerShell 里默认不可用（需 Git Bash / MSYS2 / WSL
> 提供 `make` 与 `sh`），且虚拟环境可执行文件在 Windows 位于 `.venv\Scripts\`（而非 `.venv/bin/`）。
> 因此本项目提供跨平台入口：把下文的 `make X` 换成 **`python tasks.py X`** 即可，
> 它零依赖、会自动探测 venv 位置。运行 `python tasks.py` 可列出全部任务。

```bash
# 本地开发
make install        # 装依赖
make dev            # 起网关
make test           # 跑测试（302 passed，e2e 无集群时自动跳过）
make all            # lint + typecheck + test

# 压测与校验
make bench          # 串行 vs 批处理主对标
make bench-sweep    # 批大小扫描曲线
make verify         # 仿真模型自校验（必须 PASS）
make verify-all     # 跑完全部校验脚本

# 集群
make cluster        # 建 kind 集群
make crd            # 生成并安装 CRD
make deploy         # Helm 部署
make operator       # 本地运行 Operator
make e2e            # 端到端测试（需集群）
make cluster-delete # 删除集群

# 脚本入口（不用 make 时）
python tasks.py verify-all               # 全部校验
python tasks.py verify-coldstart         # 冷启动端到端验证
python bench/verify_claims.py            # 文档数字对账
python deploy/k8s/generate_manifests.py --all   # 生成清单
```
