该部门 2027 届**软件开发工程师** JD 的优选条件原文与我的对答：

### 1.1 「有分布式、云化、容器化等软件开发经验」

**答**：我的项目三条都覆盖了。
- **容器化**：网关做了多阶段 Docker 构建，非 root 运行（uid 10001），
  用 tini 做 PID 1 保证 SIGTERM 能传到 uvicorn 触发优雅停机；
  本地用 kind 起 1 控制面 + 2 工作节点做验证。
- **云化**：通过 CRD + Operator 把服务变成声明式 API，
  `kubectl apply` 一个 `InferenceService` 就自动生成 Deployment/Service/HPA/ServiceMonitor 等 6 类资源。
- **分布式**：多副本网关 + 一致性哈希做会话粘性路由（为了复用 prefix cache），
  熔断器隔离后端故障，队列深度作为扩缩容信号——这些都是分布式系统的典型模式。

> **追问预案：你们的服务怎么扩容？**
> 网关是无状态的（批队列在进程内，但每个请求只在一个副本内完成），
> 所以用 HPA 按自定义指标横向扩副本。
> 关键点是**扩展维度解耦**：网关按 QPS 扩，vLLM 推理进程按 GPU 显存扩，两者不绑死。
> 我把 vLLM 当独立 Pod 而不是嵌进网关进程，就是为了这个。

### 1.2 「熟悉 TCP/IP 等通信协议原理」

**答**：我项目里有两处直接用到协议层知识。
- **SSE 流式**：这是 SSE over HTTP/1.1 chunked。我踩过的坑是
  **必须回 `X-Accel-Buffering: no`**，否则 nginx 会攒满缓冲才下发，
  用户感知是"卡一下然后全部出来"，TTFT 指标也会失真。
  另外要周期性发注释行 `: ping` 做保活，防止中间设备按空闲超时切断长连接。
- **连接复用**：调用 vLLM 时用 httpx 的连接池，
  复用 TCP 连接避免每请求三次握手；并且**批量执行**而不是每请求一次连接。

> **追问预案：SSE 和 WebSocket 怎么选？**
> SSE 是单向（服务端→客户端）、基于 HTTP、天然支持断线重连（浏览器会自动重连），
> 实现简单且能穿大多数企业代理；WebSocket 是全双工，但要处理心跳、重连、协议升级，
> 且部分代理不友好。
> 推理场景是"客户端发一次请求、服务端持续推 token"，单向足够，所以选 SSE。
> 如果要做实时语音对话（需要打断、双向流），那 WebSocket 或 WebRTC 才合适。

> **追问预案：HTTP/2 对这个场景有什么影响？**
> HTTP/2 多路复用能让多个流共享一条 TCP 连接，省掉连接数开销；
> 但对 SSE 有个副作用：HTTP/2 的流控在连接级别共享窗口，
> 慢客户端可能拖累同连接的其他流。因此生产上常见做法是
> **SSE 走 HTTP/1.1 + 多个 keep-alive 连接**，或给 HTTP/2 单独调流控窗口。

### 1.3 「掌握常用的数据结构和算法」

**答**：我在三个地方用了具体的数据结构，都是为解决问题选的：
- **堆（heapq）**：准入队列用最小堆做优先级调度。
  这里有个设计点：优先级会随"等待时长"动态变化（老化），
  如果维护"可更新优先级的堆"就需要索引堆，实现复杂。
  我用**惰性堆**：弹出时用当前时刻重算优先级，若变得更优先就 `heapreplace` 重新入堆。
  每次只可能重塑队首，复杂度仍是 O(log n)。
- **分桶（bucket）**：按 prompt 长度分桶，让同批请求长度接近。
  这解决的是 padding 浪费——批内最长 prompt 决定计算量，
  如果长短混在一起，短请求的算力全浪费在 padding 上。
- **令牌桶**：限流用令牌桶而不是固定窗口，
  因为固定窗口在窗口切换处会出现"双倍突发"，而令牌桶能平滑限速又允许合法突发。

> **追问预案：为什么老化能保证有界等待？**
> 有效优先级 = 基础优先级 − 等待时长 / aging_ms。
> 等待越久，减掉的越多，有效优先级越小（越小越优先）。
> 所以任意请求的等待时间上界约为 `aging_ms × 优先级跨度`。
> 我用单测验证了这一点：一个 priority=100 的请求等待 250ms 后
> 会排在刚入队的 priority=0 请求前面。

### 1.4 「负责单元测试、静态检查、本地构建、集成测试」

**答**：这方面我做得比较系统。

## 2. 连续批处理（核心亮点，必被深挖）

### 2.1 连续批处理相比静态批处理解决了什么？【对应"调度引擎"bullet】

**答**：核心差异在**调度粒度**。

- **静态批处理**：一批请求同时开始、同时结束。
  问题有两个：① 队头阻塞——短请求必须等长请求跑完；
  ② 生成阶段每步长度不齐，padding 浪费严重。
  结果是"批越大吞吐越高"很快失效，因为长尾请求把整体拖死。

- **连续批处理（iteration-level scheduling）**：**每个解码步重新组装批次**。
  已完成的请求立即退出、让出显存，新请求立刻补位。
  这样长尾请求不再拖累整体。

我的实现里，批构建由三个约束控制：
`max_batch_size`（显存与 attention 计算量）、
`max_batch_tokens`（KV Cache 占用峰值）、
`max_wait_ms`（批构建最长等待）。
第三个是**延迟与吞吐的显式权衡旋钮**：调大→批更大吞吐更高但 TTFT 变差；
调小→延迟低但吞吐下降。

### 2.2 你的批构建具体怎么做的？【对应"调度引擎"bullet】

**答**：分两步。

**第一步：准入与优先级（`engine/queue.py`）**
- 双阈值准入控制：队列长度上限 + 在途 token 预算，超限直接抛背压，返回 429。
  **为什么快速失败而不是排队**：GPU 吞吐固定，无限排队不会变快，
  只会让延迟无界增长 + 显存被在途请求的 KV Cache 吃光，最终 OOM 把全部请求一起干掉。
- 加权优先级 + 老化：有效优先级 = 基础优先级 − 等待时长/aging_ms。

**第二步：发车判定（`_drain`）**
发车条件（满足任一）：
1. 批内请求数达到 `max_batch_size`；
2. 批内 token 预算达到 `max_batch_tokens`；
3. **队首请求等待时长超过 `max_wait_ms`**。

> **这里我踩过一个坑（主动讲，显得真实）**：
> 我最初的发车条件里多了一条"队列已空就发车"。
> 结果低并发时每个请求单独成批，**批处理收益归零**。
> 因为"队列短暂为空"恰恰是"应该再等一会儿聚合"的信号，而不是发车信号。
> 这是我从一个失败的单测里发现的。

### 2.3 批内各请求的结果怎么分开回传？【对应"流式网关"bullet】

**答**：**每个请求一个私有 chunk 队列**（`RequestHandle`）。

批执行器 `_run_batch` 用 `asyncio.gather` 并发跑批内每个请求，
每个请求从后端拿到 token 后 `push` 到自己那个队列；
调用方（网关）从自己的队列读。

这样做的好处：
1. **天然多路复用**：一个批里 16 个请求各自流式输出，互不干扰；
2. **慢客户端不阻塞批内其他请求**——如果用单一共享队列，
   一个慢客户端就会拖累整条链路；
3. 关闭时投递一个 sentinel 对象表示结束，消费侧 `async for` 自然退出。

### 2.4 批内某个请求失败了会怎样？【错误隔离】

**答**：**错误被隔离在该请求内，不影响同批其他请求。**

`_run_batch` 用 `asyncio.gather(..., return_exceptions=True)`，
单个请求抛异常只终结它自己，批执行器继续等其他人完成，
最后把该请求的 handle 关闭、上报 `failed` 指标。

我在单测里专门验证了这点：一个"一半请求失败"的假后端，
失败请求收到空流、成功请求正常拿到内容，
而且 `failed_batches` 是 0——**单请求失败不应该把整批判定为失败**。

### 2.5 显存超卖怎么防？【三层防护】

**答**：三层，从入口到运行时逐层收紧。

1. **准入控制（网关侧）**：队列中所有在途请求的
   `prompt_tokens + max_tokens` 之和不得超过 `max_queue_tokens` 预算，超出直接 429。
   这里用的是**保守估算**（假设每个请求都生成满 max_tokens），宁可少放一些也不能 OOM。
2. **动态降批（调度器侧）**：按显存水位自适应收缩批大小——
   水位 < 60% 用满批大小；60%~85% 线性衰减到一半；> 85% 降到 1。
   这是软背压，比直接拒绝更平滑。
3. **Runtime**：vLLM 自己会做 preemption/swap。
   我额外用 Prometheus 采集 KV Cache 水位，作为 HPA 的扩容信号和告警依据。

> **追问预案：为什么不直接把显存预算设小一点？**
> 设小了吞吐上不去（批被限制），设大了会 OOM。
> 所以我的做法是"预算 + 动态调节"：预算给一个偏保守的基线，
> 再用水位反馈动态降批，这样在正常情况下能跑满，压力大时能自动退让。

## 3. 性能数据与调优（会被追问数字来源）

### 3.1 「4.9 倍是怎么测的？」【必须答清楚】

**答**：用**同并发窗口对比**，这是关键。

**朴素做法的问题**：串行组给高并发、批处理组给低并发，
比出来的差异里混进了"并行度不同"的因素，结论不可信。

**我的做法**：每个并发档位都跑一组串行基线，两组使用**相同的在途请求数**。
此时唯一变量是"一个解码步服务几个请求"。

**具体配置**：并发 16，每组 64 请求，prompt 256 token，生成 32 token。

| 场景 | QPS | TTFT P99 | GPU 利用率 |
|---|---|---|---|
| 串行 | 4.63 | 3362.0 ms | 5.8% |
| 连续批处理 b=16 | 22.60 | 81.5 ms | 58.9% |

**更重要的是负面对照**：串行实现的吞吐**与并发无关**（并发 1/16/32 都是 ≈4.7 QPS），
增加并发只会让 TTFT 从 51ms 线性恶化到 6676ms（130 倍）。
这从反面论证了批处理的必要性。原始数据在 `bench/results/` 里。

### 3.2 「数据是真实 GPU 测的吗？」【诚实回答，加分项】

**答**：**不是，是耗时模型仿真**，我在性能报告里明确标注了这个边界。

**为什么用仿真**：真实 vLLM 需要 Linux + CUDA，我这台是 Windows 且 WSL2 还没装；
而且 8GB 显存的卡只能跑小模型量化版，绝对值也不具备普适性。

**为什么仿真数据仍然可信**：我的时间模型基于 Transformer 推理的**物理事实**：
- **Prefill 受算力限制**：处理 P 个 prompt token 的时间 ≈ P × 单token成本，**线性**；
- **Decode 受显存带宽限制**：每步要把全部模型权重从显存读一遍，
  这是**固定成本**，被批内所有请求摊薄 —— 这正是批处理收益的来源。

**关键是我做了独立验证**：写了 `bench/verify_model.py`，
用**解析公式独立预测**耗时，再与实测墙钟对比，偏差 < 3%。
如果仿真实现有 bug，这个偏差会立刻暴露——
事实上第一版就暴露了（偏差 91%），我发现仿真按"每请求独立计时"
而不是"整批共享一次解码步"，修正后才通过。

> 这个回答的杀伤力：**主动暴露方法论的局限 + 给出交叉验证证据**，
> 比声称"我测了真卡"然后答不上细节强得多。

### 3.3 「批大小是不是越大越好？」【体现调参思维】

**答**：不是，存在最优值。我的批大小扫描曲线（并发固定 16）：

| 批大小 | QPS | TTFT P50 |
|---|---|---|
| 1 | 2.39 | 6359.1 ms |
| 4 | 5.74 | 2163.9 ms |
| 8 | 11.38 | 777.4 ms |
| **16** | **22.18** | **75.1 ms** |
| 32 | 21.02 | 100.2 ms |

吞吐随批大小**单调上升至饱和**，在批大小 = 并发数（16）时达到峰值；
继续增大反而略降——因为单步成本含 `decode_per_request_ms × B` 项
（attention 计算量随批线性增长），批填不满时这部分纯亏。

**生产调参建议**（我写在报告里）：
- `max_batch_size` 取"并发 P95 × 1.2"与显存上限的较小值；
- `max_wait_ms` 高负载 10-20ms，**低负载调 0-5ms 甚至关闭批处理**——
  因为并发为 1 时批处理反而更慢（我的数据：2.44 vs 4.74 QPS），
  额外的屏障与任务调度开销成为纯损耗。

### 3.4 「你的网关引入多少额外延迟？」【体现工程严谨】

**答**：我用 Echo 后端（每 token 延迟恒定、与并发无关）单独测了网关的纯开销：

| 并发 | QPS | TTFT P50 | TTFT P99 |
|---|---|---|---|
| 16 | 999.79 | 6.0 ms | 10.8 ms |
| 64 | **1602.59** | 9.8 ms | **10.5 ms** |

**结论**：网关自身在 64 并发下能跑 1603 QPS、TTFT P99 只有 10.5ms。
这说明**瓶颈完全在推理侧，不在协议/调度框架**，
也说明网关具备横向扩展空间——可以通过加副本应对更多接入连接。

> 这个测试的设计意图是"把网络协议开销和 GPU 计算开销解耦"，
> 否则你无法回答"你的框架本身吃掉多少性能"。

## 4. Kubernetes Operator 与控制面

### 4.1 为什么要用 Operator？【对应"弹性与交付"bullet】

**答**：因为"部署一个模型服务"这件事**有运维知识但缺少声明式表达**。

用 Helm 或一堆 YAML 的问题是：它们只描述"创建什么资源"，
不描述"服务应该处于什么状态"。模型服务的运维知识包括：
副本数怎么定、健康探针怎么配、扩缩容指标用哪个、
灰度怎么推进、失败怎么回滚——这些逻辑没有地方安放，
只能写成文档靠人执行。

Operator 的做法是把这些知识编码成**调和循环**：
用户只声明"我要 Qwen-1.5B，最少 2 副本最多 8 副本，队列深度超 16 就扩"，
Operator 负责把实际状态持续收敛到期望状态。

**我的 CRD 叫 `InferenceService`**，一个 CR 自动生成 6 类资源：
Deployment、Service、HPA、ServiceMonitor、PrometheusRule、PDB。

### 4.2 调和循环怎么做到幂等？【核心概念题】

**答**：三个具体手段。

1. **调和函数不保存任何本地状态**，只做
   "读期望状态 → 读实际状态 → 计算差异 → 收敛差异"。
   给定同样的输入必然给出同样的输出。
2. **资源名由 CR 名 + 角色唯一确定**，不含随机数或时间戳。
   所以第二次调和算出的资源名和第一次完全一样，走的是 `patch` 而不是重复 `create`。
3. **变更检测用 spec hash**：把 spec 的稳定哈希写进 Pod 模板 annotation，
   只有哈希变化才触发滚动更新；不相关的调和不会重启 Pod。

我用单测验证了幂等性：**第二次调和必须产生零个写操作**。
第一次跑完把生成的资源当作"已存在"，再跑一次，
断言 `create/update/delete` 三个动作的数量都是 0。

> **追问预案：Deployment 的 selector 为什么不能包含 spec hash？**
> 因为 K8s 规定 `spec.selector` **创建后不可修改**。
> 如果把 hash 放进去，第二次调和就会尝试改 selector，被 API Server 拒绝。
> 所以 selector 只由「CR 名 + 角色」决定，这两个都是不可变的。

### 4.3 孤儿资源怎么清理？【体现细节意识】

**答**：两种情况分开处理。

1. **CR 删除时**：靠 `ownerReference` 级联回收。
   我给每个子资源都写了 ownerReference（带 controller: true）。
   如果手写删除逻辑，很容易漏删——比如新增了一种资源类型忘了加，
   最后留下"没人管但仍在消耗 GPU"的 Pod。
2. **资源不再属于期望状态时**（比如灰度回滚后 canary 的 Deployment/Service）：
   调和时遍历已存在的资源，不在期望集合里的就删。
   但**必须先做安全检查**——只删带 `app.kubernetes.io/managed-by: aetherserve-operator`
   标签的资源，避免误删别人的资源。这个安全检查我专门写了测试。

> **追问预案：怎么判断一个资源"归本 CR 所有"？**
> 优先用 **ownerReference 的 uid**，而不是按资源名做子串匹配。
> 后者在多个 CR 名字互为前缀时会张冠李戴，进而误删别人的资源。
> 这点我特意改过一次实现。

### 4.4 Operator 重启后已存在的 CR 会被接管吗？

**答**：会，但必须显式注册 `resume` 处理器——**这是最容易被漏掉的点**。

kopf 里 `on.create` 只处理新建对象、`on.update` 只处理 spec 变更。
Operator 重启后，已存在的 CR 既不触发 create 也不触发 update，
如果没有 `on.resume`，**这些 CR 就永远不会被重新调和**。

我的实现里 `create / update / resume` 共用同一个调和函数——
这本来就是对的："无论怎么被触发，都让实际状态收敛到期望状态"。

### 4.5 灰度发布怎么自动回滚？【对应"稳定性与发布"bullet】

**答**：我把灰度决策写成了**纯函数状态机**（`operator/canary.py`），
输入是 spec + 当前状态 + 观测指标，输出是决策。

**判定顺序本身是设计**：
1. 未启用 / 已终态 → 原样返回；
2. **样本不足 → 保持不动**（不推进也不回滚）；
3. **错误率超限 → 立即回滚**；
4. 健康 → 权重按 step 推进；
5. 推进到 100% → Promoted。

**两个关键安全设计**：
- **最小样本量门禁**：样本少于 `min_samples` 时绝不推进。
  否则一个只收到 3 个请求、恰好全成功的灰度版会被误判为"健康"直接全量——
  这是灰度发布最经典的事故模式。
- **失败立即止损**：错误率一旦超阈值，不做"再观察一轮"，直接归零。
  灰度的价值就是限制爆炸半径，犹豫等于放大损失。

**为什么写成纯函数**：如果把这些 if/else 混在调和循环里，
验证方式就只剩"改集群 + 等 5 分钟看结果"，成本高到没人会测。
抽成纯函数后，我可以在毫秒级单测里覆盖全部边界
（样本不足、错误率恰好等于阈值、终态不再推进等 27 个用例）。

### 4.6 监控不可用时灰度会怎样？【fail-safe 设计】

**答**：**停在原地，不会盲目推进。**

`_fetch_canary_metrics` 查 Prometheus 失败时返回"空指标"，
而空指标的 `request_count = 0 < min_samples`，
于是走"样本不足"分支 → 权重保持不变。

这是刻意的 **fail-safe（失败安全）而不是 fail-open（失败放行）**：
监控挂了说明我们对灰度状态"看不见"，此时最安全的动作是什么都不做。
如果设计成 fail-open（拿不到指标就当健康），监控一挂就会全量发布，风险极大。

## 5. 弹性伸缩

### 5.1 HPA 用什么指标？为什么？

**答**：用两类自定义指标（可同时启用）：

| 指标 | 语义 | 特点 |
|---|---|---|
| `queue_depth` | 队列深度（Pods 类型 AverageValue） | **反应最快**——积压是扩容的前兆 |
| `kv_cache` | KV Cache 显存水位 | **最准确**——反映真实瓶颈 |

**为什么要两个**：单用队列深度容易"过早扩容"（瞬时尖峰也扩），
单用显存水位会"过晚扩容"（水位上去时延迟已经劣化了）。
两者结合可以做到"提前扩容 + 精准收敛"。

### 5.2 扩容和缩容的策略为什么不对称？

**答**：刻意做成"扩容快、缩容慢"。

- **扩容**：`stabilizationWindowSeconds: 0`，策略是最多翻倍。
  流量尖峰时必须尽快加副本，否则请求堆积。
- **缩容**：`stabilizationWindowSeconds: 300`（默认 5 分钟），策略是最多减半。
  因为缩容抖动会直接导致请求失败——副本刚起来就又缩掉，
  还不如保持稳定。这个窗口也是 K8s 的默认行为，是经过实践检验的。

> **追问预案：扩容需要多久？卡在哪？**
> 我实际没有在真实集群测过完整的扩容时间线（WSL2 环境还没搭好），
> 所以简历里我**没有写"XX 秒内完成扩容"这个数字**——
> 我对未实测的数据一律不写。这一点我可以在架构上说明：
> 扩容时间 = HPA 指标采集周期（15-30s）+ HPA 决策 + Pod 调度 + 镜像拉取 + 启动就绪。
> 其中镜像拉取通常是瓶颈，所以我把网关镜像做成多阶段构建保持瘦小，
> 并且用 startupProbe 给足冷启动时间（failureThreshold 30 × 5s = 150s）。

## 6. 稳定性设计

### 6.1 熔断器状态机怎么工作？

**答**：三态机。

```
CLOSED ──连续失败 ≥ threshold──▶ OPEN
  ▲                               │
  │                    (recovery_timeout 到期)
  │                               ▼
  └──半开探测全成功──────── HALF_OPEN
```

- **CLOSED**：正常放行，累计连续失败数。
- **OPEN**：快速失败，返回 503 + Retry-After，**不耗时等待后端**。
- **HALF_OPEN**：只放行少量探测请求（`half_open_max_calls`）。
  成功 → 判定恢复，回到 CLOSED；失败 → **立即重新打开**，不给劣化后端机会。

**为什么推理服务必须有熔断**：后端一旦变慢或挂掉，
没有熔断的网关会把请求全部堆积在等待上，
连接池耗尽、事件循环被 pending 请求占满，最终**整个网关失去服务能力**——
这就是级联故障。熔断的价值是把资源留给还有救的请求，并给后端恢复的时间窗。

> **追问预案：熔断和限流的区别？**
> 限流是"**保护自己不被上游打死**"，针对的是流量大小（令牌桶按租户限速）；
> 熔断是"**保护自己不被下游拖死**"，针对的是依赖健康度。
> 两者正交，我的网关里都有。
> 还有第三种：背压（队列满直接 429），那是"保护下游 GPU 不被自己压垮"。

### 6.2 双维度令牌桶是什么？

**答**：**请求数 + token 数两个维度同时限流。**

只按请求数限流的问题是：单请求成本差异极大
（10 token 和 4096 token 相差两个数量级），
一个租户用 10 个超大请求就能把 GPU 打爆，但请求数还远没到限。

所以我的实现里两个桶（`TenantRateLimiter`）：
- 请求桶：容量 `burst`，速率 `rps`；
- token 桶：按预估成本（prompt + max_tokens）扣减。

**实现细节**：用单调时钟 `time.monotonic()` 而非墙钟，
避免 NTP 校时回拨导致令牌凭空增加。
单请求成本超过整桶容量时只记账不拒绝——
否则超大请求会因为"永远凑不够令牌"而被永久阻塞。

### 6.3 优雅停机怎么保证不丢请求？

**答**：三步顺序很关键——**我先置停机标志、再等排空、最后关队列**。

```
1. _running = False          # 停止接受新请求，但分发循环继续派发已准入的
2. 等待队列深度归零（带超时）   # 已准入的请求全部执行完
3. 关闭队列 + 终止分发循环     # 然后才释放资源
```

**我踩过的坑（真 bug）**：我最初写成"先关队列再停循环"，
结果分发循环的 `get()` 因为队列关闭立即返回空列表、
已准入的请求**永远没人处理**——那不是优雅停机，是静默丢请求。
这个 bug 是我从一个挂死的单测里定位出来的。

**另一个相关 bug**：队列关闭后，分发循环拿到空结果会立刻重试，
形成 **busy-spin 把事件循环饿死**，导致已提交请求的消费者协程拿不到执行机会。
修法是在空结果时 `await asyncio.sleep(0)` 主动让出。

**容器层的配合**：`terminationGracePeriodSeconds: 60`，
并且 Dockerfile 用 **tini 作为 PID 1** —— 否则 SIGTERM 可能不会传到 uvicorn 子进程，
优雅停机逻辑根本不会触发。

### 6.4 客户端断开后 GPU 还在算吗？

**答**：不会，我做了**取消传播**。

网关在流式返回时捕获 `asyncio.CancelledError`（客户端断开时 Starlette 会取消这个协程），
然后调用 `engine.cancel(request_id)`。

**这里我也踩过坑**：最初的 `cancel()` 只设置了 handle 上的取消位，
但没有设置**队列里那个 item** 的取消位。
结果是：已排队但还没派发的请求仍然会被正常执行——
客户端已经断开了，GPU 还在白烧算力。
修法是双位置标记 + `wake()` 唤醒分发循环立即重排。

## 7. AI / 大模型相关

### 7.1 你对 vLLM 和 PagedAttention 的理解？【对应"AI 工程"技能】

**答**：vLLM 的核心贡献是用**操作系统的虚拟内存思想管理 KV Cache**。

传统实现的 KV Cache 按"最大序列长度"预分配连续显存，
问题是：① 内部碎片严重（实际长度往往远小于最大值）；
② 外部碎片导致无法复用；③ 实际显存利用率常常只有 20-40%。

PagedAttention 把 KV Cache 切成固定大小的 **block**（类似内存页），
用 block table 做逻辑到物理的映射。
好处是：显存按需分配、块可以不连续、**不同序列可以共享块**（prefix caching）。

**这直接决定了我项目里的两个设计**：
1. **批大小不能只按请求数定**——真正约束是 KV Cache block 的数量，
   所以我的批约束里有 `max_batch_tokens` 这个维度，而不只是 `max_batch_size`；
2. **一致性哈希做会话粘性路由**——同一会话（相同 messages 前缀）落到同一实例，
   可以复用已计算的 prefix cache，对长 system prompt 场景能显著降低 TTFT。

### 7.2 Prefill 和 Decode 为什么分开看？

**答**：因为两者瓶颈完全不同，这决定了优化方向。

| 阶段 | 计算特征 | 瓶颈 | 优化手段 |
|---|---|---|---|
| **Prefill** | 矩阵乘，算术强度高 | **算力（FLOPs）** | 算子融合、chunked prefill |
| **Decode** | 每步只生成 1 token，要把全部权重读一遍 | **显存带宽** | **批处理**（摊薄权重读取） |

**批处理之所以有效，正是因为 Decode 受显存带宽限制**：
读一次权重是固定成本，批内 N 个请求共享这一次读取。
批大小 1 时，大部分时间花在"读权重"这个无法避免的空转上，GPU 利用率极低；
批越大，同一份权重服务越多请求，利用率越高。

这也是我仿真时间模型的物理依据：
`decode_step_ms(B) = decode_base_ms × 摊薄系数(B) + decode_per_request_ms × B`。

### 7.3 模型量化了解吗？

**答**：了解主流方案的基本权衡。

| 方案 | 精度 | 显存 | 说明 |
|---|---|---|---|
| FP16/BF16 | 基准 | 基准 | 训练与高精度推理 |
| **AWQ** | 较好 | ~1/4 | 激活感知权重量化，对激活异常值友好，**推理场景常用** |
| **GPTQ** | 较好 | ~1/4 | 逐层量化 + 校准集，生态成熟 |
| INT8 | 好 | ~1/2 | 兼容性好，压缩比低 |
| FP8 | 很好 | ~1/2 | 需要新硬件支持（H100 及以后） |

我项目里默认用 `Qwen2.5-1.5B-Instruct-AWQ`，
因为 8GB 显存要留出 KV Cache 空间，量化后权重只占约 1GB，剩余空间可以支撑更大的批。
**注意量化和批处理是相互促进的**：量化省下的显存可以换更大的批 → 更高吞吐。

### 7.4 如果让你做 RAG，你会怎么设计？【应对 AI 应用工程师岗】

**答**：我会按"离线索引 + 在线检索增强"两段设计，并特别注意工程细节：

**离线**：文档解析 → 分块（chunking）→ 向量化 → 写入向量库。
分块策略是效果的关键：固定长度会切断语义，我倾向**按标题层级分块 + 重叠窗口**，
并保留元数据（来源、页码）用于引用溯源。

**在线**：query 改写 → 向量检索（+ 关键词混合召回）→ 重排（rerank）→
拼进 prompt → 交给推理服务。

**工程要点**（这部分才是我项目经验能迁移的地方）：
1. **推理服务复用**：RAG 的生成环节就是我的推理平台，
   多租户、限流、批处理、熔断全部可以直接复用；
2. **缓存**：相同问题的检索结果 + 生成结果分层缓存；
3. **可观测**：检索命中率、上下文长度分布、生成延迟都要埋点——
   否则"效果不好"无法定位是检索问题还是生成问题。

> **追问预案：怎么评估 RAG 效果？**
> 分两层：检索层看 Recall@K 和 MRR；生成层看忠实度（faithfulness，答案是否只依据检索内容）
> 和相关性。没有人工标注时，可以用 LLM 做裁判（LLM-as-judge），但要固定 prompt 和模型版本以保证可比性。

## 8. 网络与协议追问

### 8.1 你的流式输出在 nginx 后面会出问题吗？

**答**：会，有两个必须处理的点。

1. **响应缓冲**：nginx 默认会缓冲上游响应（`proxy_buffering on`），
   把 token 攒起来一起发，用户感知是"卡一下然后全部出来"。
   必须回 `X-Accel-Buffering: no` 头，或者在 nginx 配置 `proxy_buffering off`。
   我在网关的 SSE 响应头里直接带了 `X-Accel-Buffering: no` 和
   `Cache-Control: no-cache, no-transform`，并且有单测断言这两个头存在。
2. **超时**：SSE 是长连接，`proxy_read_timeout` 默认 60s，
   如果模型生成慢（比如长文本），连接会被切断。
   解法是周期性发注释行 `: ping` 做保活，让连接持续有数据流动。

### 8.2 为什么 SSE 帧必须是单行 JSON？

**答**：因为 SSE 协议用换行分隔事件。
一个事件由若干 `field: value` 行组成，以**空行**结束。
如果 JSON 里有未转义的换行，客户端会把它当成"两条 data 行"或"事件结束"，
导致数据损坏。

所以我用 orjson 做紧凑单行序列化（默认行为），
并且写了一个测试专门验证"含换行的字符串被转义而不是原样输出"。

### 8.3 为什么不用 gRPC 做推理接口？

**答**：生态和接入成本。

- **生态**：OpenAI 兼容协议意味着业务方**零改造迁移**——
  他们已经在用 openai SDK 或 LangChain，改个 base_url 就能接我的服务。
  gRPC 需要为每种语言生成 stub，接入成本高。
- **流式**：SSE 在浏览器和 HTTP 客户端里都是原生支持的；
  gRPC 的 server streaming 需要 HTTP/2 和专门的客户端库。
- **调试**：curl 就能测 SSE，gRPC 要 grpcurl 或写代码。

**但 gRPC 有它的场景**：如果做的是**内部服务间**的高频小消息通信
（比如调度器与推理 worker 之间传控制指令），
gRPC 的二进制编码和 Protobuf schema 演进能力更好。
所以我的设计里，南北向（对外）用 HTTP/SSE，东西向（内部）的扩展方向是 gRPC。

## 9. 行为与软技能问题

### 9.1 你做的项目里最难的部分是什么？

**答**：最难的是**让批处理真正生效**，不是写代码难，而是"看不见问题在哪"。

我最初跑压测，发现关批处理和开批处理的吞吐差不多。
日志显示批大小一直是 1。我以为是调度器的并发参数问题，
调了半天参数都没用。

后来我写了一个诊断脚本，把 `_drain` 的每次决策都打出来，
才发现是发车条件里那条 `or not self._heap`：
队列一空就立刻发车，导致每个请求都单独成批。
而"队列空"在低并发下恰恰是常态，所以批处理完全失效。

**这件事给我的教训**：性能问题的定位不能靠猜参数，
要**在做决策的地方打点**，让程序自己告诉你在哪里走了岔路。
后来我把这个习惯延续下来了——现在项目里所有关键决策点（发车、灰度推进、资源清理）
都有明确的日志或指标。

### 9.2 你是如何保证代码质量的？

**答**：几个具体做法，不是"我很注意"这种空话。

1. **把逻辑和 I/O 分离**：调度、批构建、灰度决策、清单生成全部写成纯函数。
   这样能用毫秒级单测覆盖全部边界，不用起集群。
2. **用权威工具做校验**：生成的 K8s 清单用官方客户端反序列化成类型化模型，
   而不是"能 dump 成 YAML 就算对"。
3. **不写脆弱的测试**：我踩过 Windows 定时器粒度的坑，
   后来把时序断言全部改成确定性断言（计费模型），把时间相关的验证移到压测脚本。
   提交前连跑 3-4 次确认无 flaky。
4. **数字必须可复现**：我写了 `verify_claims.py` 自动对账
   "文档里的数字 vs 原始数据"，防止文档间不一致。

### 9.3 如果让你重做，你会改什么？

**答**：三个方向。

1. **批处理引擎要支持"批内动态进出"**。我现在的实现是"批派发后跑到底"，
   严格说这是**静态批 + 等满发车**，不是真正的连续批处理。
   真正的连续批处理应该让完成的请求立刻退出、新请求在解码中途补位。
   受限于时间我用了更简单的模型，但这是最重要的一步演进。
2. **GPU 调度器插件没做完**。我设计了显存感知的 Filter/Score 策略，
   但只完成了设计，代码还没写。这是我下一步要补的。
3. **缺真实集群验证**。Operator 的逻辑我用单测覆盖了 92%，
   但集群 I/O 层（`handlers.py`）必须在真实集群跑过才算数。
   WSL2 环境搭好后我会做端到端验证。

> **主动说出这些局限很重要**：面试官最反感的是把没做的东西说成做了。
> 我明确知道边界在哪，并且说得出下一步怎么做。

### 9.4 为什么选择华为云软件研发部？

**答**：三个理由，都是具体的。

1. **技术方向匹配**：这个部门做云化、容器化方向的软件开发，
   和我项目的技术栈（Kubernetes、Operator、微服务、可观测性）高度重合。
   我看到 JD 的优选条件里写"有分布式、云化、容器化等软件开发经验"，
   这正是我过去几个月在做的事情。
2. **能接触到规模化系统**：我做的是单机单卡的仿真验证，
   GPU 利用率优化到 58.9% 已经很开心了；但在华为云的规模下，
   调度、隔离、成本优化这些问题的复杂度是完全不同的量级，
   我想在这种规模下学习真正的工程实践。
3. **AI 与云原生的交叉点**：这个部门同时有 AI 应用工程师岗位，
   需要大模型应用开发能力。我的推理平台项目正好在两者的交叉点上，
   既能做基础设施又能碰模型落地。

## 10. 反问环节（一定要问，体现主动性）

面试最后的"你有什么想问我的"是加分机会。推荐 3 个问题，按优先级：

1. **「这个岗位的同学，日常工作中云原生和 AI 应用的比例大概是怎样的？」**
   ——展示你关心具体工作内容，且暗示你两者都能做。

2. **「团队目前在推理/模型服务这块，遇到的最大工程挑战是什么？」**
   ——展示你对技术深度的兴趣，也能收集真实信息判断是否值得去。
   如果对方回答"调度和成本"，你可以顺势聊你的显存装箱设计。

3. **「如果我加入，前三个月最希望我产出什么？」**
   ——展示结果导向，也让你知道该往哪准备。

**不要问**：薪资细节（HR 环节再谈）、加班情况（容易被扣分）、
"你们用什么技术栈"（官网/JD 上有的信息，问了显得没做功课）。

## 附录 A：手写代码题准备方向

结合岗位 JD 与我的项目，重点准备：

| 题型 | 为什么 | 我的项目关联 |

| **一致性哈希** | 分布式必备 | 我实现了带虚拟节点的一致性哈希做会话粘性 |
| **滑动窗口最大值** | 限流/监控统计 | 可以关联到请求速率统计 |
| **单例 / 工厂 / 策略模式** | 设计模式 | 我的 backends 就是策略模式 + 工厂注册 |

**手写代码时的加分细节**（面试官会注意到）：
- 先问清边界条件（空输入、超大输入、并发安全要求）；
- 写出函数签名和类型注解再动手；
- 主动说复杂度，并说明为什么选这个数据结构；
- 写完自己给一个测试用例走一遍。
